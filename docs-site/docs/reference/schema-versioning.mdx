# Schema versioning & deprecation policy

This policy governs every machine-readable JSON document emitted by `e2e-healer --json`.
It applies to `RepairSummary`, `RefusalReport`, `SuiteSummary`, and `ReviewReport`.

## Status and scope

Schema `1.0` is the original published baseline. Schema `2.0` added the `refusal`
discriminator, closed refusal reasons, and evidence bundles. Schema `2.1` added the optional
`CandidateEvidence.ast_lock` detail object, and `2.2` the optional `EvidenceBundle.provenance`
object, which records the provider, model, endpoint and redaction counts for the evidence a run
sent. Schema `2.3` is the current output contract: it adds the executed graph `path`, the
`loop_budget`, `CandidateEvidence.next_step` and the `termination` of a repair or refusal. All three
are compatible minor changes under the rules
below. The contract is emitted by the CLI, documented for GitHub Action workflows, and consumed by
the bundled Playwright Reporter and review-bot examples. A schema change is evaluated against this
published contract, not merely against direct runtime checks in this repository.

The schema version identifies the JSON payload contract. It is independent from the
`e2e-healer` package or GitHub Action release version.

## Version format

Schema versions use `MAJOR.MINOR`:

- A **major** version signals a change that a conforming consumer cannot safely process
  without an update.
- A **minor** version signals a backwards-compatible addition that a conforming consumer may
  safely ignore until it is ready to use it.

The producer emits one schema version for each result. Nested result documents, such as
`SuiteSummary.results`, use the same schema version as their enclosing summary.

## Compatibility rules

The following changes are compatible and require a minor version bump:

- Adding an optional field with a documented default or absence behavior.
- Adding an optional member to an existing object when its absence does not change the meaning
  of existing fields.
- Adding a new optional detail object whose presence consumers may ignore.
- Clarifying documentation without changing the payload's meaning.

The following changes are breaking and require a major version bump:

- Removing, renaming, or changing the type of an existing field.
- Making an optional field required, or changing a field's default or absence behavior.
- Changing the meaning of an existing field, including the success semantics of
  `is_success` or an Action `outcome`.
- Adding or removing a top-level `kind` discriminator value.
- Adding, removing, or changing a value in a closed enum, including `RefusalReason`.
- Changing result nesting, ordering guarantees, or whether a document is emitted for an
  existing command outcome.

Closed enums and `kind` values are deliberately treated as breaking: consumers commonly use
exhaustive dispatch, and accepting an unknown outcome can hide an unsafe repair decision.

## Consumer requirements

Consumers must read `schema_version` before interpreting the payload:

1. Reject an unsupported **major** version with a clear error that includes the received and
   supported versions. Do not infer behavior from unrecognized keys or `kind` values.
2. Accept a newer **minor** version within a supported major version by ignoring unknown
   optional fields.
3. Reject an unknown `kind` or closed-enum value even when the major version appears
   supported. Such a payload indicates a producer or policy violation and must not be silently
   treated as a successful repair.
4. Branch on documented fields only. Consumers must not depend on JSON key ordering or on
   undocumented fields.

The current composite Action forwards summary JSON to a workflow-provided file path rather
than parsing it. Workflow authors and programmatic wrappers that read that file are responsible
for these checks.

## Producer requirements

Before emitting a new schema version, maintainers must:

1. Classify every proposed change using the compatibility rules above.
2. Update the Pydantic output models, contract tests, CLI documentation, and Action examples
   together.
3. Add consumer coverage for every newly emitted `kind` and every rejection path.
4. Record the schema change, compatibility classification, and migration instructions in the
   release notes.

A major-version release must not reuse an earlier major version for a different payload shape.

## Deprecation and migration

When a new major version ships:

- Announce the change and its migration guide in the release notes and documentation before
  recommending the new major to Action users.
- Keep the previous major's documentation, examples, and versioned Action/CLI release
  available for **at least 12 months** after the successor ships.
- Maintain the previous major for critical compatibility or security fixes during that window
  when feasible. Consumers needing fixed old behavior should pin the corresponding Action tag
  or package release.
- After the window, mark the old major unsupported. It remains available by its immutable
  release tag, but new releases need not emit or test it.

The CLI does not currently provide a `--schema-version` compatibility mode. Until such a mode
exists, preserving an older output contract means pinning the prior Action or package release.

## Applying this policy to repair refusals

`RefusalReport` is emitted as a version `2.0` result, carrying the terminal refusal reason and
its evidence bundle. This was a major change because it made the `refusal` discriminator and
closed `RefusalReason` enum public. Future additions must choose one of these designs:

- Add optional refusal evidence without changing the meaning of its `kind`, `reason`, or
  `loop_count`; this is a minor change.
- Introduce another `kind` or add a value to the closed `RefusalReason` enum; this is a major
  change under this policy and requires consumer migration guidance.

This rule prevents a refusal from being mistaken for an ordinary unsuccessful repair by a
workflow that has not been updated to recognize it.

### Worked example: schema 2.1

Schema `2.1` added `ast_lock` (`reason`, `node_kind`, `line`) to rejected candidates so a
guardrail refusal reports what the structural lock caught instead of only a message string. It was
classified under this policy as follows:

- It is an optional detail object whose absence does not change the meaning of any existing
  field, so it is a **minor** change. A consumer written against `2.0` keeps working by ignoring
  it.
- `ast_lock.reason` is deliberately an **open string**, not a closed enum, because adding a value
  to a closed enum would be a major change. Consumers must tolerate reasons they do not
  recognize.
- It is `null` when another check, not the AST lock, refused the candidate, so it must not be used
  to decide whether a `guardrail_violation` occurred; that is the job of `reason`.

### Worked example: schema 2.2

Schema `2.2` added `provenance` (`provider`, `model`, `endpoint`, `mode`, `redaction_applied`,
`redaction_count`) to the evidence bundle so a run records where its evidence went and whether the
boundary replaced anything first:

- The field is optional and absent (`null`) when the repair loop never ran, so a consumer written
  against `2.1` keeps working by ignoring it: a **minor** change.
- `provider` is an **open string**, not a closed enum, so supporting a new backend is not a contract
  change. Consumers must tolerate values they do not recognize; that is why it is not closed.
- `mode` is a closed enum (`local` / `remote`) whose value is derived from the endpoint address. A new
  mode, or a change to how an existing one is derived, is a **major** change: a wrapper that gates on
  `mode === "remote"` would otherwise start sending evidence differently without noticing.
- `redaction_applied` and `redaction_count` describe what the boundary did, not what it guarantees;
  a count of `0` must not be read as "this evidence was harmless".

### Worked example: schema 2.3

Schema `2.3` made the repair loop's control flow reviewable: `evidence.path` lists every graph node
the run executed, each candidate's `next_step` names where the router sent the run after judging
it, `evidence.loop_budget` states the cap, and `termination` (`verified`, `refused`,
`budget_exhausted`, `verification_failed`) says how the run ended:

- `path`, `loop_budget` and `next_step` are new optional fields with a documented absence (an empty
  list and `null` when the loop never ran), so a consumer written against `2.2` keeps working by
  ignoring them: a **minor** change.
- Node names in `path` and `next_step` are **open strings**, not a closed enum, because the graph's
  nodes are meant to be extended. A new node must not be a contract change; consumers must tolerate
  names they do not recognize.
- `termination` is a **closed** enum on a new field. Adding the field is minor; adding a value to it
  later is **major**, because a wrapper that branches on `budget_exhausted` to retry with a larger
  cap must not silently misread a new outcome.
- `termination` is derived from `reason`, `is_success` and the last candidate's `rejection`, so it
  never contradicts them. It does not replace `reason`: `refused` covers six reasons, which `reason`
  still tells apart. `LoopEvidence.stage` was left unchanged, since adding the Diagnoser to that
  closed set would have been a major change; `path` records every node instead.
