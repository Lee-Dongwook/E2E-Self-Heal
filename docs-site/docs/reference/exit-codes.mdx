# Exit codes & JSON output

`--json` emits one machine-readable result to stdout; human output stays on stderr so CI can
parse it safely. The [JSON output reference](./json-output) documents every field and shows
payloads captured from real runs.

## Exit code contract

- `e2e-healer heal <path>` exits `0` when the test is healed and `1` for a refusal.
- `e2e-healer heal` (suite mode) exits `0` only when every discovered failing test is healed and
  the final full-suite rerun passes. A `--dry-run` suite always exits `1`.
- `e2e-healer review` exits `0` after a completed review (wrappers branch on `has_findings`) and
  `1` when the model provider failed (`is_complete: false`).
- Any command exits `2` for invalid input, a sandbox denial, or an unreadable diff, and emits no
  JSON.
- When the test already passes and no `--log` was given, `heal <path>` and `review` exit `0` and
  emit no JSON. Exit `1` with no JSON means the CLI crashed.

The [JSON output reference](./json-output#when-a-document-is-emitted-and-the-exit-code) has the
full table of outcomes, documents and exit codes.

## JSON contract

Every result contains a `schema_version` and `kind` discriminator. Current output is schema
`"2.3"`: version 2 introduced the first-class `"refusal"` kind and its closed reason taxonomy,
2.1 added the optional `ast_lock` detail on rejected candidates, 2.2 the evidence `provenance`,
and 2.3 the executed graph `path`, the `loop_budget`, each candidate's `next_step` and the
result's `termination` (all compatible minor changes).
Consumers must reject unsupported schema majors and unknown `kind` or refusal-reason values, and
must ignore unknown optional fields within a supported major.
See the [schema versioning and deprecation policy](./schema-versioning) for the compatibility
and migration rules.

| Field | `RepairSummary` | `RefusalReport` | `SuiteSummary` | `ReviewReport` |
| --- | --- | --- | --- | --- |
| `schema_version` | `"2.3"` | `"2.3"` | `"2.3"` | `"2.3"` |
| `kind` | `"repair"` | `"refusal"` | `"suite"` | `"review"` |
| `test_script_path` | ✔ | ✔ | — | ✔ |
| `is_success` | ✔ | `false` | ✔ | — |
| `reason` | — | ✔ | — | — |
| `loop_count` | ✔ | ✔ | — | — |
| `instructions` | ✔ | — | — | — |
| `termination` | ✔ | ✔ | — | — |
| `evidence` | ✔ | ✔ | — | — |
| `results` | — | — | ✔ (`RepairSummary` / `RefusalReport`) | — |
| `findings` | — | — | — | ✔ |

The `evidence` object records the parsed failure, failing selector, DOM diff context, a
content-hashed ARIA snapshot reference, ordered repair candidates, ordered loop-stage
outcomes, and the ordered path of graph nodes the run executed. Snapshot content is not embedded
in output; its reference points to the original
workspace artifact as provenance when available. The digest is over the redacted extracted
snapshot, not the source `error-context.md` bytes. Sensitive structured values and URL query
values are redacted.

### `ast_lock` on a rejected candidate

When the structural AST lock refuses a candidate, that entry in `evidence.candidates` carries an
`ast_lock` object. Otherwise the field is `null`: candidates refused by other checks (a stale
line, a per-line scope gate, selector or shadow verification) explain themselves only in
`rejection`.

| Field | Type | Meaning |
| --- | --- | --- |
| `reason` | string | Why the lock refused. Currently `disallowed_ast_change`, `original_parse_error`, or `patched_parse_error`. An **open** set: ignore values you do not recognize. |
| `node_kind` | string or `null` | The tree-sitter node type where the original and patched trees first diverge. This can be a container such as `program` when a statement was added or removed, not the added statement itself. |
| `line` | integer or `null` | 1-based line of that node in the patched source, or of the parse error. |

A run that ends in `reason: "guardrail_violation"` can still have candidates without `ast_lock`,
because the per-line scope gates also raise guardrail violations. Use `ast_lock` to learn *what*
the lock caught, not to decide *whether* a guardrail violation occurred.

### Example: guardrail refusal with `ast_lock` detail

Captured from the real repair graph with a stubbed provider that keeps proposing
`const submit = page.locator('#new'); await page.goto('/admin');` for
`const submit = page.locator('#old');`. It passes the per-line gates but appends a statement, so
only the AST lock refuses it. Each of the three attempts produced a candidate like this one; the
example keeps the first candidate and the first loop event, and leaves out `provenance`, which a
stubbed provider does not meaningfully have. `path` shows the three rejected attempts going
straight back to the Patch Generator, and `termination` is `refused` because the reason is a
guardrail violation, not the loop cap.

```json
{
  "schema_version": "2.3",
  "kind": "refusal",
  "test_script_path": "t.spec.ts",
  "reason": "guardrail_violation",
  "is_success": false,
  "loop_count": 3,
  "evidence": {
    "parsed_error": "Error: waiting for locator('#old') timed out\ncall log: locator('#old') timed out",
    "failing_selector": "#old",
    "dom_diff_context": [],
    "aria_snapshot": null,
    "candidates": [
      {
        "loop_count": 0,
        "source": "llm",
        "instructions": [
          {
            "line": 1,
            "original": "const submit = page.locator('#old');",
            "replacement": "const submit = page.locator('#new'); await page.goto('/admin');",
            "reason": "adds navigation",
            "selector": ""
          }
        ],
        "memory_score": null,
        "shadow_score": null,
        "selector_counts": {},
        "test_passed": null,
        "outcome": "rejected",
        "rejection": "AST lock rejected the patch (disallowed_ast_change: program at line 1); only locator strings, timeouts, and wait methods may change",
        "ast_lock": {
          "reason": "disallowed_ast_change",
          "node_kind": "program",
          "line": 1
        },
        "next_step": "patch_generator"
      }
    ],
    "loop_history": [
      {
        "loop_count": 0,
        "stage": "memory_lookup",
        "outcome": "miss",
        "details": { "score": 0.0, "error": null, "instruction_count": null, "reason": null }
      }
    ],
    "path": [
      { "node": "memory_lookup", "loop_count": 0 },
      { "node": "diagnoser", "loop_count": 0 },
      { "node": "patch_generator", "loop_count": 1 },
      { "node": "patch_generator", "loop_count": 2 },
      { "node": "patch_generator", "loop_count": 3 },
      { "node": "refusal_finalizer", "loop_count": 3 }
    ],
    "loop_budget": 3
  },
  "termination": "refused"
}
```
